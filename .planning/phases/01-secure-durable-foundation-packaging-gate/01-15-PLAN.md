## Phase Goal

**As a** learner, **I want to** install Danesh on a clean Windows or macOS machine and have it keep my data durable, private and safe from crashing engines, **so that** I can trust it with my documents and study history.

<objective>
Close PLAT-05 (default-deny network egress, D-17, ROADMAP success criterion 2): Core and every engine host deny Node-level network access from their first line; a pure policy with an empty production allowlist, exact host normalization and a consent-grant seam is the only controlled exception mechanism; the download, web-research and update-check paths exist only as denied stubs; the «اتصال به اینترنت» System check row proves zero attempts across all processes; and a network-monitored end-to-end scenario with positive controls shows the proof is real.

Why this plan comes late (wave 12): the full proof needs the real engine hosts (Plan 01-09), CI wiring (Plan 01-10) and Core/host restarts (Plan 01-14) to exist so it can watch them all. Plan 01-07 already blocks Chromium traffic (layer L1); this plan adds the Node layer, the policy skeleton and the monitors. This plan is the first one that may drop `--allow-unbound` from the features gate, because it binds the last unbound scenarios (`@plan-01-15`).

Deliberate deviation from the wording of D-17 ("the only module allowed to import network APIs"): the test-only monitors under `tools/egress/` are exempt from the network-module lint rules, exactly as `tools/fetch-probes.ts` is, because they exist to observe the network; no `apps/` or `packages/` file may import `tools/` (new boundary rule) and ADR 0001's Security section records the deviation (Plan 01-16 Task 3).

Purpose: PLAT-05 verified, not asserted — a product promise ("no hidden transfers") with an automated test that fails when it breaks.
Output: egress package (guard, policy, broker skeleton, stubs), egress-zero check, test-only monitors, bound Gherkin, CI wiring, local Windows evidence.
</objective>
